# api

FastAPI service on Postgres. It is a uv project: `pyproject.toml` declares
compatible ranges, `uv.lock` is committed and is what actually gets installed.

## Runtime contract

Set by the Deployment in the infra repo; changing any of it means changing a
manifest there too.

| | |
| --- | --- |
| Listen | `$PORT`, default `8080`, on `0.0.0.0` |
| Liveness | `GET /healthz` — 200, touches nothing |
| Readiness | `GET /readyz` — 200, or 503 if a configured database does not answer `SELECT 1` inside 1s |
| User | uid/gid `65532`, no capabilities |
| Filesystem | read-only root, no writable path needed anywhere |
| Config | environment only |

`GET /` returns the same body as `/healthz`. That route exists because the base
Deployment still points its readiness probe at `/`, left over from the
`traefik/whoami` stand-in — keeping it makes the image swap a one-line overlay
change instead of a manifest edit.

## Configuration

| Variable | Default | Notes |
| --- | --- | --- |
| `PORT` | `8080` | 1–65535; anything else fails at startup |
| `LOG_LEVEL` | `INFO` | case-insensitive |
| `DATABASE_URL` | unset | `postgres://`, `postgresql://` and `postgresql+asyncpg://` all accepted; the first two are rewritten to the asyncpg driver, because the cluster Secret holds the libpq form that `psql` also has to understand |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | unset | when set, traces are exported over OTLP/gRPC and FastAPI is instrumented; when unset the OTel exporter stack is never even imported |
| `OTEL_SERVICE_NAME` | `api` | resource attribute `service.name` |

Empty strings read as unset. Validation happens once, when `api.config` is
imported, so a bad value stops the container instead of surfacing later as a
confusing 500.

## Endpoints

```
GET  /healthz          200
GET  /readyz           200 | 503
GET  /                 200
POST /v1/items         201   {"name": "..."}
GET  /v1/items         200   ?limit=1..200 (default 50), newest first
GET  /v1/items/{id}    200 | 404
```

Without `DATABASE_URL` the probes still pass and the `/v1/items` routes answer
**503** with a plain explanation. A process with no database is a degraded
process, not a broken one, and only the routes that genuinely need storage
should fail.

## Running locally

```sh
uv sync                                  # or `make dev` from the repo root
uv run uvicorn api.main:app --port 8080  # no database: items routes → 503
```

With Postgres — `make lab-up` in the infra repo brings up the kind lab; reach
its database either by port-forward or from inside the cluster:

```sh
kubectl -n app port-forward svc/postgres 5432:5432   # in another shell
export DATABASE_URL=postgres://app:localdev@localhost:5432/app

uv run python -m api.migrate             # create the schema
uv run python -m api.seed                # optional, idempotent
uv run uvicorn api.main:app --port 8080
```

The credentials above are the throwaway literals in the infra repo's local
overlay; the cloud overlays get theirs from Secret Manager instead.

## Migrations

Alembic, async, with the migration scripts inside the package
(`src/api/migrations/`) so they ship in the wheel and the image can run them
with no extra files copied in.

```sh
uv run python -m api.migrate             # upgrade to head
uv run python -m api.migrate 0001_create_items
uv run alembic revision --autogenerate -m "add thing"   # needs DATABASE_URL
```

`python -m api.migrate` is the form meant for the future Argo CD PreSync Job:
same image as the Deployment, different command, non-zero exit stops the sync
before new pods roll. `alembic.ini` exists only for the local CLI — nothing in
the cluster reads it, and its `sqlalchemy.url` is deliberately blank so a stale
value can never point a migration at the wrong database.

The initial migration is plain Postgres: `uuid` and `timestamptz` are core
types, so it needs no `CREATE EXTENSION` and no superuser. Ids are generated by
the application (`uuid4`), which is why `items.id` has no server default.

## Tests

```sh
uv run pytest                            # unit only; no database, no network
TEST_DATABASE_URL=postgresql+asyncpg://app:localdev@localhost:5432/app \
  uv run pytest -m integration           # against a real Postgres
```

Data access sits behind the `ItemRepository` protocol in `repository.py`. The
route tests bind an in-memory implementation to the same dependency the
Postgres one uses in production, so they cover validation, status codes and
serialisation with nothing running. The integration tests cover what a fake
cannot: the migration, the real `uuid`/`timestamptz` columns, and transactions.
They are skipped unless `TEST_DATABASE_URL` is set, so the default run needs no
container.

## Layout

```
src/api/
  config.py         pydantic-settings; validated at import
  logging.py        stdlib JSON logging
  middleware.py     raw-ASGI access log (method, path, status, duration)
  main.py           app factory + lifespan (engine, tracer provider)
  db.py             async engine, session factory, bounded SELECT 1
  models.py         SQLAlchemy models
  repository.py     ItemRepository protocol + Postgres implementation
  schemas.py        request/response models
  dependencies.py   FastAPI dependency wiring
  telemetry.py      OTel, imported only when an endpoint is configured
  routes/           health.py, items.py
  migrations/       Alembic env + versions/
  migrate.py        `python -m api.migrate`
  seed.py           `python -m api.seed`, idempotent
```

## Image

Multi-stage: a builder installs `uv.lock` into `/opt/venv`, the runtime stage
copies that venv onto a digest-pinned `python:3.12-slim` and runs as uid 65532.
Nothing is written at runtime — no bytecode, no logs to disk, no temp files —
which is what lets `readOnlyRootFilesystem: true` work with no `emptyDir`
mounted anywhere. If that ever changes, the infra repo needs a writable volume
before the image does.
